# 0410 项目后端结构与代码说明

## 1. 文档目的

这份文档用于说明当前项目在 B/S 化之后的后端结构、启动链路、接口职责和关键代码逻辑，目标是：

- 讲清楚项目为什么现在属于 B/S 架构
- 讲清楚 4100 / 4101 两个服务分别做什么
- 讲清楚新增后端代码的职责分层，而不是只看见几个零散的 `.py` 文件
- 方便在答辩或向导师汇报时，能按“为什么这样做、具体怎么跑、每段代码做什么”来解释

这份文档描述的是**当前已经跑通的实际结构**，不是理想化重构后的结构。

---

## 2. 当前整体运行形态

### 2.1 为什么现在算 B/S 架构

当前项目已经不是最初那种“直接双击 HTML 文件、本地拼静态页”的形态，而是变成了：

- 浏览器访问统一入口 `https://www.hychemistry.cn/`
- 由 4100 这个 Web 宿主承载主页和静态展项
- 由 4101 这个后端服务提供动态能力
- 浏览器通过 HTTP(S) 接口访问 AI 助手、TTS、健康检查、周期表后端 API

因此它已经符合典型 B/S（Browser / Server）模式：

- Browser：浏览器访问页面、发起接口请求、播放音频、打开摄像头
- Server：后端负责接口、代理、AI 能力封装、HTTPS 提供、周期表 API 服务

### 2.2 当前不是“彻底重写后的前后端分离工程”

当前项目仍然保留了大量原有静态页面，例如：

- `主页.html`
- `pages/Chemical_Epics/化学史诗.html`
- `pages/Chemical_equation/equation_cloud.html`
- `pages/chemistry_lab/lab.html`
- `pages/chemistry_kill/game.html`
- `pages/surprise.html`

所以它更准确地说是：

> 一个统一 Web 宿主下，挂载多个原有静态展项，再补一个统一后端能力层。

这是一种“**最小改动整合**”方案，而不是把所有页面完全改造成统一模板工程或前后端完全分离项目。

## 3. 后端分层总览

从职责上看，当前后端相关代码可以分成三层：

### 3.1 启动编排层

- [`start_bs.py`](../server/start_bs.py)

职责：

- 统一启动整个 B/S 运行链路
- 同时拉起 4100 和 4101 两个 Flask 进程
- 注入端口、证书、内部反代地址等环境变量
- 监控两个子进程是否异常退出
- 任一子进程提前退出时，联动关闭整个系统

### 3.2 Web 承载层

- [`web_host.py`](../server/web_host.py)

职责：

- 对外承载主页和静态页面
- 作为 4100 的 HTTPS Web 宿主
- 提供少量动态接口的同源代理
- 控制 HTML/API 缓存策略

### 3.3 业务能力层

- [`backend_server.py`](../server/backend_server.py)
- [`aigent_service.py`](../server/aigent_service.py)
- [`chem_tools.py`](../server/chem_tools.py)
- [`vision_service.py`](../server/vision_service.py)
- [`rag_engine.py`](../server/rag_engine.py)
- [`mcp_server.py`](../server/mcp_server.py)
- [`pages/Periodic_Table/app.py`](../pages/Periodic_Table/app.py)

职责：

- `backend_server.py`：统一后端服务入口，提供 AI、视觉、TTS 与维基代理接口，并复用周期表 Flask app
- `aigent_service.py`：封装大模型对话、SSE 流式输出和 TTS 上游调用
- `chem_tools.py`：6 个确定性化学工具（元素查询、摩尔质量、配平、反应检索、安全信息、知识检索）
- `vision_service.py`：多模态图片识别，识别结果再进入工具链校验
- `rag_engine.py`：BM25 + LSA 向量 + RRF 的本地混合检索
- `mcp_server.py`：把化学工具以 MCP 协议对外提供（6 工具 + 3 资源）
- `Periodic_Table/app.py`：保留原独立引入仓库中的周期表后端能力

## 5. 启动链路与端口分工

## 5.1 实际启动入口

当前建议的统一启动命令是：

```bash
uv run python server/start_bs.py
```

这条命令会同时启动两个服务：

- 4100：`web_host.py`
- 4101：`backend_server.py`

### 5.2 为什么要同时拉起两个服务

因为两个服务的职责不同：

- 4100 负责给用户访问网页
- 4101 负责提供动态能力接口

如果只启动 4100：

- 主页能打开
- 静态页面能访问
- 但 AI 助手会离线
- `/api/aigent/*` 和 `/speech/synthesize` 无法工作
- 4100 的代理接口会返回后端不可用

如果只启动 4101：

- 周期表 Flask 首页和 `/api/elements`、`/api/phases/*` 等 API 可用
- AI 助手接口和 TTS 接口可用
- 但主页 `主页.html`、静态展项、统一 Web 入口都不会由 4101 提供

因此完整体验必须两个都启动。

### 5.3 端口分工

| 端口 | 服务 | 面向谁 | 作用 |
| --- | --- | --- | --- |
| `4100` | `web_host.py` | 对外用户入口 | 主页、静态页面、同源代理 |
| `4101` | `backend_server.py` | 内部动态能力 | 周期表后端、AI 聊天、TTS、健康检查 |

## 6. HTTPS 与证书策略

### 6.1 证书选择逻辑

在 [`start_bs.py`](../server/start_bs.py) 中，证书由 `resolve_tls_pair()` 决定：

- 优先使用系统证书：
  - `/etc/ssl/dongdongkc.top.pem`
  - `/etc/ssl/dongdongkc.top.key`
- 如果系统证书不存在，则回退到仓库内证书：
  - `certs/0410-web.crt`
  - `certs/0410-web.key`

这意味着当前部署既支持：

- 正式域名证书环境
- 本地 fallback 测试证书环境

### 6.2 为什么 4100 也必须走 HTTPS

不是只有 4101 才需要 HTTPS，4100 也必须走 HTTPS，原因有：

- 浏览器对摄像头调用有安全上下文要求
- 浏览器对音频播放和部分媒体权限在 HTTPS 下更稳定
- 域名场景下如果主页是 HTTPS，但接口是 HTTP，会触发混合内容问题
- 用户访问的是正式域名，需要让入口页本身可信

### 6.3 为什么要做同源代理

当前主页前端使用的是：

- `/api/health`
- `/api/aigent/bootstrap`
- `/api/aigent/chat`
- `/speech/synthesize`

它们由 4100 代理到 4101，而不是前端直接跨端口调用 4101。

这样做的作用是：

- 保持浏览器端同源调用模型
- 减少跨域和证书差异问题
- 避免主页写死不同端口逻辑
- 避免混合内容风险
- 让前端只知道“同源站点有这些接口”，不需要知道内部能力实际跑在 4101

## 7. `start_bs.py` 代码功能说明

文件：[`start_bs.py`](../server/start_bs.py)

### 7.1 `resolve_tls_pair()`

作用：

- 判断当前使用哪一套 TLS 证书
- 优先系统证书，回退仓库内证书

这是整个 HTTPS 启动链路的统一证书入口。

### 7.2 `start_process(label, command, extra_env)`

作用：

- 用 `subprocess.Popen()` 启动子进程
- 注入额外环境变量
- 打印子进程 PID

这里把“启动后端”和“启动 Web 宿主”的公共逻辑统一起来。

### 7.3 `main()`

作用：

- 调用 `resolve_tls_pair()` 取证书
- 分别启动 4101 和 4100 两个服务
- 向两个服务注入不同的环境变量
- 注册 `SIGINT` / `SIGTERM` 信号处理
- 如果任一子进程异常退出，则联动关闭另一个服务

### 7.4 它注入了哪些关键环境变量

对 4101：

- `BACKEND_HOST=0.0.0.0`
- `BACKEND_PORT=4101`
- `BACKEND_SSL_CERT_FILE`
- `BACKEND_SSL_KEY_FILE`

对 4100：

- `WEB_HOST=0.0.0.0`
- `WEB_PORT=4100`
- `WEB_SSL_CERT_FILE`
- `WEB_SSL_KEY_FILE`
- `INTERNAL_BACKEND_ORIGIN=https://127.0.0.1:4101`
- `INTERNAL_BACKEND_VERIFY_SSL=0`

其中 `INTERNAL_BACKEND_VERIFY_SSL=0` 的含义是：

- 4100 访问内部 4101 时，不要求校验本机内部 HTTPS 证书
- 这是为了简化本机环回代理场景

## 8. `web_host.py` 代码功能说明

文件：[`web_host.py`](../server/web_host.py)

### 8.1 它的定位

它不是业务后端，而是：

> 一个“HTTPS 静态宿主 + 少量反向代理”的薄层。

### 8.2 `/`

```python
@app.get("/")
def index():
    return send_from_directory(ROOT_DIR, "主页.html")
```

作用：

- 保持 `主页.html` 为正式入口
- 用户访问 4100 根路径时，直接返回主页

这保证了用户原有“主页作为总站入口”的要求没有被打破。

### 8.3 `serve_file(filename)`

```python
@app.get("/<path:filename>")
def serve_file(filename):
```

作用：

- 继续直接托管原项目中的静态文件
- 例如：
  - `Chemical_Epics/化学史诗.html`
  - `Chemical_equation/equation_cloud.html`
  - `Periodic_Table/交互式元素周期表/交互式元素周期表3D.html`
  - 图片、音频、视频资源

这也是为什么当前项目不需要把所有静态页重写进 Flask 模板系统。

### 8.4 `proxy_backend(path)`

作用：

- 将允许代理的请求转发到 4101
- 保留：
  - 请求方法
  - 请求体
  - 查询参数
  - 上游响应内容与状态码

它本质上实现了一个轻量反向代理。

### 8.5 当前代理白名单

`web_host.py` 只代理少量动态接口：

- `/api/health`
- `/api/aigent/bootstrap`
- `/api/aigent/chat`
- `/api/aigent/chat/stream`（SSE，逐块透传，不能缓冲完整响应）
- `/api/aigent/vision`
- `/api/wiki/summary`
- `/api/wiki/image`
- `/speech/synthesize`

这说明它不是“通用 API 网关”，而是只给站点需要的能力开白名单。

### 8.6 缓存策略：`disable_cache(response)`

作用：

- HTML 和 `/api/*`：不缓存
- 静态资源：长缓存

具体原因：

- HTML 不缓存：避免用户仍拿到旧页面
- `/api/*` 不缓存：避免助手状态和接口结果滞后
- `/speech/synthesize` 当前是单独代理路径，不属于 `request_path.startswith("/api/")` 这一分支
- 静态资源长缓存：提升图片、音频、JS、CSS 加载效率

## 9. `backend_server.py` 代码功能说明

文件：[`backend_server.py`](../server/backend_server.py)

### 9.1 为什么直接 `from Periodic_Table.app import app`

当前代码是：

```python
from Periodic_Table.app import app
```

这意味着：

- 没有再新建一套第二 Flask app 去转发周期表
- 而是直接复用 `Periodic_Table/app.py` 里的 Flask app 对象
- 再在这个 app 上继续挂项目自己的接口

所以 4101 实际上是：

> “周期表后端能力 + AI 助手能力 + TTS 能力”的统一服务。

同时要注意：

- 4101 不只是 API 端口
- 因为它直接复用了 `Periodic_Table.app`
- 所以访问 `https://...:4101/` 时，根路径仍会打开周期表 Flask 首页
- 只是当前它不再承担主页默认周期表入口职责

这样做的好处是：

- 少一层额外转发
- 直接复用周期表已有模板与 API 能力
- 改动更小

### 9.2 `CORS(app, resources={r"/api/*": {"origins": "*"}})`

作用：

- 给 `/api/*` 路径增加跨域容忍

这里要明确边界：

- 当前明确放行跨域的是 `/api/*`
- `/speech/synthesize` 并不在这条 CORS 规则里

因此主页里的 TTS 之所以稳定，不是因为 4101 所有接口都允许浏览器直接跨域访问，而是因为：

- 主页前端请求的是 4100 同源路径 `/speech/synthesize`
- 再由 4100 代理到 4101

### 9.3 `/api/health`

作用：

- 返回极简健康检查结果

用途：

- 主页判断“小幻语 · 在线 / 离线”
- 便于快速确认 4101 是否活着

### 9.4 `/api/aigent/bootstrap`

作用：

- 返回 AI 助手基础信息
- 包括：
  - `assistant_name`
  - `intro`

用途：

- 当前端首次展开小幻语面板时，先请求这个接口
- 用它给用户展示第一段欢迎文案

### 9.5 `/api/aigent/chat`

输入：

```json
{
  "history": [
    {"role": "user", "content": "你好"},
    {"role": "assistant", "content": "你好呀"}
  ]
}
```

输出成功示例：

```json
{
  "ok": true,
  "reply": "……"
}
```

失败时：

- 如果上游模型请求失败，返回 `502`
- 因为当前失败不在浏览器本身，而在后端调用上游模型的阶段

### 9.6 `/speech/synthesize`

输入：

```json
{
  "text": "你好",
  "language": "zh-CN"
}
```

输入校验：

- 文本不能为空
- 文本长度不能超过 `1000`

这里有两层限制：

- 路由层 [`backend_server.py`](../server/backend_server.py) 对公开 HTTP 接口限制为 `1000` 字
- 服务层 [`aigent_service.py`](../server/aigent_service.py) 中 `TTSClient.synthesize()` 的通用上限仍是 `20000` 字

这样设计的原因是：

- 路由层更关注网页端的时延、稳定性和资源控制
- 服务层保留更宽的泛化能力边界，便于后续在别的调用场景复用

返回：

- 二进制音频流
- `mimetype` 由 TTS 返回结果决定
- 响应头：
  - `X-Speech-Language`
  - `X-Speech-Model`

### 9.7 `/api/aigent/vision`

输入：

```json
{
  "image": "data:image/jpeg;base64,...",
  "question": "这张图里的方程式配平了吗"
}
```

流程：

- 缺少图片时直接返回 `400`
- 调用 `vision_service.analyze_image()`，失败返回 `502`
- 识别结果为方程式时，自动调用 `balance_equation()` 做确定性二次校验
- 识别结果为装置 / 试剂时，自动补充安全信息
- 返回 `{ok, result, model, degraded, chain}`，`chain` 记录实际使用的模型链路

### 9.8 `/api/aigent/chat/stream`

以 Server-Sent Events 推送 Agent 全过程：

- `status`：思考 / 调用工具等状态
- `tool`：工具名与参数、结果摘要
- `delta`：逐字增量文本
- `done`：结束标记

异常时以 `event: error` 事件收尾，保证前端能正常结束渲染。对应地，`web_host.py` 使用 `stream=True` 逐块转发，并设置 `X-Accel-Buffering: no` 避免代理层缓冲。

### 9.9 `/api/wiki/summary` 与 `/api/wiki/image`

用于元素详情页的维基百科拓展，由服务端代为访问维基：

- `summary` 参数：`lang`（仅 `zh` / `en`）与 `title`（非空）
- 服务端请求 `https://{lang}.wikipedia.org/api/rest_v1/page/summary/{title}`
- User-Agent 必须携带联系方式，否则维基会按机器人流量返回 `403 Too Many Reqs`
- 摘要结果在内存中缓存 `600` 秒，降低上游压力
- `image` 参数为缩略图地址，仅允许 `https` 且域名属于 `upload.wikimedia.org` / `thumb.wikimedia.org`，避免被当作任意 URL 代理（SSRF）

这样大陆网络环境下的客户端无需直连维基，也能正常显示摘要与配图。

## 10. `aigent_service.py` 代码功能说明

文件：[`aigent_service.py`](../server/aigent_service.py)

### 10.1 为什么这一层独立存在

原因是路由层应该尽量薄：

- `backend_server.py` 只负责接 HTTP 请求、做输入校验、返回响应
- 具体怎么调上游大模型、怎么调 TTS，不应该混在路由函数里

这样分层后：

- 路由逻辑更清楚
- AI 能力更好测试和替换
- 上游服务变动时，只改服务层

### 10.2 `SYSTEM_PROMPT`

作用：

- 定义“小幻语”这个角色的人设、说话风格、交互原则

它决定的是：

- 助手的身份设定
- 回答语气
- 化学安全优先的行为规则

### 10.3 `INTRO_MESSAGE`

作用：

- 定义初次打开网页助手时展示的欢迎文案

这段文案通过 `/api/aigent/bootstrap` 暴露给前端。

### 10.4 `_normalize_history(history)`

作用：

- 清洗前端传来的聊天历史

它会过滤掉：

- 非 `user` / `assistant` 的角色
- 非字符串内容
- 空白内容

这样做可以避免脏数据直接送进上游模型。

### 10.5 `chat_with_aigent(history)`

作用：

- 组织最终的聊天消息列表
- 在最前面插入 `SYSTEM_PROMPT`
- 调用 DeepSeek 的聊天接口
- 返回模型回复内容

失败处理：

- 如果上游返回非 `200`，抛出错误
- 上层路由捕获后，转换成 `502`

### 10.6 `TTSSettings`

作用：

- 统一管理 TTS 参数

包括：

- `ws_url`
- `model`
- `voice`
- `format`
- `sample_rate`

当前代码里允许通过环境变量覆盖这些值。

当前代码默认值中：

- `TTS_MODEL=cosyvoice-v3-flash`
- `TTS_VOICE=longxiaochun_v3`

如果部署环境中显式注入了 `TTS_VOICE`，则运行时会以环境变量为准，而不是代码默认值。

### 10.7 `TTSClient.synthesize(text, language)`

作用：

- 通过 WebSocket 调 DashScope TTS
- 发送三段任务消息：
  - `run-task`
  - `continue-task`
  - `finish-task`

三段的含义：

- `run-task`：创建 TTS 任务，声明模型与参数
- `continue-task`：真正发送要合成的文本
- `finish-task`：告诉服务端本轮文本已结束，可以收尾输出音频

为什么不是普通 HTTP：

- 这个 TTS 接口是 WebSocket 协议
- 音频数据以二进制分片的方式不断返回
- 最终拼成完整音频

返回值：

- `audio: bytes`
- `meta: {media_type, model, language}`

### 10.8 为什么 TTS 不直接从前端调上游

原因：

- API key 不应直接暴露在浏览器端
- 前端不适合直接持有外部上游密钥
- 前端直连还会引入跨域、鉴权、协议处理复杂度
- 统一由后端封装，前端只需 `fetch -> blob -> Audio.play()`

## 11. `Periodic_Table/app.py` 代码功能说明

文件：[`Periodic_Table/app.py`](../pages/Periodic_Table/app.py)

### 11.1 它的定位

这个文件不是这次新写出来的周期表实现，而是：

### 11.2 `DATA_FILE`

作用：

- 使用基于当前文件目录的绝对路径解析

这保证它不依赖启动时的工作目录。

### 11.3 `load_data()`

作用：

- 启动时读取元素数据
- 调用 `remap_element_category()` 重分类
- 缓存到 `data_cache`

这是为了避免每次请求都重复读取 JSON 文件。

### 11.4 `remap_element_category(element)`

作用：

- 把原始元素分类映射到当前页面使用的分类 slug

例如：

- `alkali metal -> alkali-metal`
- `noble gas -> noble-gas`

### 11.5 `/api/elements`

作用：

- 返回完整元素数据列表

这是周期表前端最核心的数据接口之一。

### 11.6 `/api/phases/<temp_k>`

作用：

- 根据温度计算元素相态

逻辑：

- 温度低于熔点：固态
- 熔点与沸点之间：液态
- 高于沸点：气态
- 缺少数据时：回退到已有 phase 或 unknown

### 11.7 为什么 4101 里要保留它

因为 4101 的意义不是替代主页周期表主入口，而是保留：

- 周期表 Flask 模块的独立后端能力
- 可独立访问的周期表能力入口
- 周期表 API（例如 `/api/elements`、`/api/phases/*`）

### 13.1 为什么主页入口仍是静态 3D 页

当前主页周期表按钮指向的是：

- `Periodic_Table/交互式元素周期表/交互式元素周期表3D.html`

2. **后端能力链路**
   - `Periodic_Table.app`
   - 提供周期表后端能力与 API
   - 被统一后端 4101 复用

文档里必须强调：

> 这两条链路现在不再互相替代，而是分别承担“用户入口体验”和“后端能力提供”。

## 14. 为什么采用这种分层

### 14.1 优点

- 改动面小
- 原有静态展项几乎不必重写
- 可以快速在当前机器上跑通
- 用户原有入口习惯保留较多
- 周期表独立仓库结构没有被破坏
- AI 助手完成了网页化接入

### 14.2 代价

- 项目不是标准化单体后端工程
- 也不是彻底前后端分离工程
- 项目级 Python 文件已集中到 `server/`，但仍与静态页面共用同一站点进程模型
- 静态页和动态能力是混合共存的

所以当前架构更准确的定义是：

> 在统一 HTTPS 宿主下，整合多个原生静态展项和少量动态后端能力。

## 15. 当前已知边界

这些问题在答辩中不应该刻意掩盖，而应该如实说明：

### 15.1 AI 与 TTS 依赖外部上游

- AI 助手并不是本地离线模型
- TTS 也不是本地离线语音合成
- 当前本地后端做的是“统一封装与转发”

### 15.2 `Chemical_equation` 已收住模型加载层，但识别体验仍受现场输入影响

特别是桌面端：

- 低分辨率笔记本摄像头
- 对焦差
- 手掌离镜头过近或过远
- 光照不足

这些都会导致“看得到手，但识别效果很差”。

### 15.3 周期表目前仍是“双链路共存”

但角色已经明确：

- 静态 3D 页：用户主入口
- Flask 周期表：后端能力链路

### 15.4 密钥管理已改为环境变量注入

代码库中不再存在明文密钥：

- 所有密钥通过环境变量读取
- 本地开发从项目根 `.env` 加载（已加入 `.gitignore`）
- 仓库仅保留 `.env.example` 占位模板
- 生产环境通过 `docker run --env-file /opt/element-whisper/.env` 注入

后续仍可继续加强：接入独立密钥管理服务、细化权限隔离与定期轮换。

### 15.5 当前运行使用 Flask 内建服务器，但外层已是完整生产链路

当前 4100 和 4101 都是通过各自文件末尾的 `app.run(...)` 启动的，即：

- [`web_host.py`](../server/web_host.py) 使用 Flask 内建服务器监听 4100
- [`backend_server.py`](../server/backend_server.py) 使用 Flask 内建服务器监听 4101

线上外层已补齐：

- Docker 容器（`start_prod.py` 同进程组拉起两个服务）
- 宿主机 Nginx 反向代理并终止 TLS（Let's Encrypt 证书）
- Cloudflare 代理域名

因此当前结构适合课程项目与中小规模展示；若要承载更大并发，仍应将容器内的 Flask 内建服务器替换为 Gunicorn 等多进程 WSGI 服务，并补齐日志、监控与自动重启策略。

### 15.6 当前依赖组织仍是“主项目 + 子项目共存”

当前有两套依赖组织：

- 根项目 [`pyproject.toml`](../pyproject.toml)
  - 负责 B/S 承载层当前真正需要的依赖
  - 例如：`flask`、`flask-cors`、`requests`、`websockets`、`mcp`、`numpy`、`scikit-learn`、`joblib`
- [`Periodic_Table/pyproject.toml`](../pages/Periodic_Table/pyproject.toml)
  - 保留原独立引入仓库的依赖描述

这意味着当前项目不是“所有依赖都被彻底揉成一个包”的重构结果，而是一个稳定优先的整合状态。

## 16. 导师可能追问的问题与简答

### Q1：为什么不把所有东西都塞进一个 Flask 工程？

答：

因为当前目标是最小改动整合，而不是彻底重构。原项目已经有大量可用静态页，强行全部搬进统一模板工程会显著增加回归风险。当前方案是保留静态展项原样，通过 4100 承载页面，通过 4101 补动态能力。

### Q2：为什么需要 4100 和 4101 两个端口？

答：

4100 是用户入口，负责主页和静态页；4101 是动态能力层，负责周期表 API、AI 聊天和 TTS。这样前端结构更稳定，也避免把静态宿主和业务接口混在一层里。

### Q3：为什么 4100 还要反向代理 4101？

答：

为了让浏览器端按同源接口访问动态能力，减少跨域、混合内容、证书差异和浏览器安全策略问题，尤其是域名 HTTPS 场景下更稳定。

### Q4：为什么不让前端直接调用大模型和 TTS？

答：

因为这样会暴露密钥，而且前端不适合直接承担跨域鉴权和 WebSocket TTS 协议处理。更合理的是后端统一封装，前端只负责展示和播放。

### Q5：为什么 `backend_server.py` 直接复用 `Periodic_Table.app`？

答：

这样可以直接复用原周期表 Flask 模块的已有模板、数据和 API 能力，减少一层重复封装，也符合“独立引入仓库尽量原样使用”的原则。

### Q6：为什么主页周期表入口不是 4101 的 `/`？

答：

因为用户原有的交互习惯是先进入静态 3D 周期表页，再在页内操作。4101 保留的是后端能力链路，不再承担主页的默认周期表入口职责。

## 17. 当前后端结构结论

一句话概括当前后端结构：

> 保持 `server/` 运行层文件不动，用 `start_bs.py` 统一编排，用 `web_host.py` 承载站点，用 `backend_server.py` 聚合动态能力，并把 `pages/Periodic_Table/app.py` 作为独立引入模块后端复用；通过同源代理与 HTTPS 适配，把原有静态站点稳定地收口成一个可运行的 B/S 项目。

如果后续还要继续演进，更推荐在这个稳定基线之上逐步重构，而不是一次性大搬目录。
